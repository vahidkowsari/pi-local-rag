从零使用这个 RAG Extension

目标是亲手完成一次小范围索引、查询和自动注入，再看懂 Provider 切换与索引重建。命令以当前 feat/cloud-research-rag 工作树为准；这份工作树含未提交修改，所以试用时直接加载本地 index.ts。

核对日期：2026-09-25 · 当前 HEAD：ff5254e · 当前仓库：pi-local-rag 0.4.1

1. 先建立一张心智图

RAG 是“先检索，再把找到的内容交给模型”。这套 Extension 把你的本地文档切成片段，生成向量，连同关键词索引存入 SQLite。搜索时合并 BM25 关键词分数与向量相似度；开启自动注入后，每轮提问前会检索，并把相关片段作为隐藏的 customType: "rag" 消息放入上下文。

文件 → 解析/分块 → Embedding → SQLite 索引 提问 → BM25 + 向量检索 → 可选 Rerank → Pi 上下文

这里有三个独立动作：索引负责准备资料，查询负责检查召回，自动注入负责让 Pi 在普通对话中使用检索结果。/rag off 只关闭最后一步，手动 /rag search 仍可使用。源码入口见 index.ts 与 retrieval.ts。

2. 用隔离目录完成第一次试用

先在终端切到这个仓库。下面的 Zsh 命令会创建一个临时示例文档和独立索引目录；PI_RAG_LEGACY_DIR 也指向临时目录，避免试用时触碰旧的 ~/.pi/lens 迁移路径。

cd /Users/chouchao/Desktop/rag-test/pi-local-rag
rag_trial_root=$(mktemp -d /tmp/pi-rag-lesson.XXXXXX)
mkdir -p "$rag_trial_root/docs"
cat > "$rag_trial_root/docs/webhook.md" <<'EOF'
# Webhook 签名验证

收到回调后先读取 X-Signature，再用服务端密钥计算 HMAC。
签名不一致时返回 401，不执行后续业务写入。
EOF

PI_RAG_DIR="$rag_trial_root/store" \
PI_RAG_LEGACY_DIR="$rag_trial_root/legacy" \
pi --no-extensions -e "$PWD/index.ts"

进入 Pi 后，依次输入：

/rag off
/rag index /tmp/这里替换为上一步实际的目录/docs/webhook.md
/rag status
/rag search webhook 签名验证
/rag on
路径替换：Pi 输入框不会展开 Shell 变量。先在终端运行 printf '%s\n' "$rag_trial_root/docs/webhook.md"，复制它输出的绝对路径，再填入 /rag index。首次使用本地模型可能需要下载模型文件；下载、ONNX 加载和真实 Pi 会话尚未在本轮验证。

/rag status 应看到独立的 Storage 路径、1 个已索引文件、非零 Chunks 与 Vectors。若搜索命中，再用自然语言问 Pi“这个 webhook 校验失败时应做什么？”；这才是在检查自动注入。索引命令和手动搜索成功，并不等于模型一定引用了片段，仍要看回答与源内容是否相符。

3. 常用命令按场景选择

场景命令实际作用
首次加入资料/rag index <绝对路径>扫描可索引文件，记录 tracked path，并建立索引。
检查资料能否搜到/rag search <问题>返回片段、来源位置与分数；云端查询失败时可能标注 degraded。
只找已索引文件名/rag find *.md按 glob 列出索引中的文件，不搜索内容。
文件改动后/rag refresh按 tracked paths 扫描新文件与改动文件，尽量跳过未变文件。
更改排除规则后/rag exclude dist/
/rag rebuild		排除规则写入配置；重建时才重新应用到已有索引。
换模型、维度或处理规则/rag rebuild --force重新生成全部向量；成功后切换活动索引。
控制自动注入/rag off / /rag on影响 Pi 每轮自动检索，不删除索引。
检查状态/rag status
/rag config		前者看数据、模型和重建提示；后者看配置文件问题。

/rag ext list|add|remove|reset 管理可索引扩展名。/rag clear 清空当前索引中的数据，适合你确实要清空当前 store 时使用。Pi 还注册了 rag_index、rag_query、rag_status 三个工具，Agent 可以调用；手动操作用 /rag 命令更容易观察每一步。源码见 index.ts 的 command 与 tool 注册。

4. 建议的日常工作流

  1. 先用 /rag status 确认 Storage 指向预期项目，Rebuild needed 为 no。
  2. 用 /rag index <文件或目录> 加入资料。目录很大时先用小目录验证检索效果。
  3. 用两三个具体问题跑 /rag search，检查片段内容、文件和页码或行号是否正确。
  4. 确认召回合适后用 /rag on，进行普通对话。资料更新后手动 /rag refresh。

本地模型下，索引超过 24 小时且每小时节流检查允许时，会在下一轮开始前尝试刷新；云端 Provider 默认不自动刷新，除非 cloudAutoRefresh: true。所以云端模式下，更新资料后优先主动运行 /rag refresh。实现见 indexing.ts 的 shouldAutoRefresh 和 index.ts 的 before_agent_start。

5. 配置、Provider 注册表和存储位置

PI_RAG_DIR 指定本次会话的索引目录，优先于从当前工作目录向上寻找 .pi/rag/；未指定且没有项目目录时，回退到 ~/.pi/rag/。首次 /rag index 在项目内也可能创建 .pi/rag/。所以不确定时先看 /rag status 的 Storage 字段。路径规则在 store.ts。

索引目录内的 config.json 选择当前模型和运行参数。仓库根的 provider.json 是内置注册表；如果索引目录内也有 provider.json，后者覆盖前者。Registry key（如 voyage）是配置里填写的 provider 值；type（如 voyage）决定 TypeScript 使用哪个协议适配器。JSON 不能凭空实现新的 HTTP 协议。解析代码在 provider-config.ts。

默认配置是本地 Xenova/all-MiniLM-L6-v2、384 维、无 Rerank；ragTopK=5、ragAlpha=0.4、ragScoreThreshold=0.1。ragAlpha=1 更偏向 BM25，0 更偏向向量，但前提是向量检索可用。云端临时覆盖要把 provider、model、dimensions 三者配成注册表中同一模型；只改 provider 名会因模型/维度不匹配而报错。默认值和验证见 config.ts。

6. 需要云端 Embedding 时怎么切换

建议先使用第二个独立 store 做云端试验。把下面文件写入 $rag_trial_root/cloud-store/config.json。这里选择内置 Voyage voyage-4-lite（1024 维）和 rerank-2.5-lite；请求会调用云端服务并产生相应费用。

mkdir -p "$rag_trial_root/cloud-store"
cat > "$rag_trial_root/cloud-store/config.json" <<'EOF'
{
  "ragEnabled": false,
  "embedding": { "provider": "voyage", "model": "voyage-4-lite", "dimensions": 1024 },
  "reranker": { "provider": "voyage", "model": "rerank-2.5-lite" },
  "cloudAutoRefresh": false
}
EOF

read -s "VOYAGE_API_KEY?Voyage API key: "
echo
export VOYAGE_API_KEY
PI_RAG_DIR="$rag_trial_root/cloud-store" \
PI_RAG_LEGACY_DIR="$rag_trial_root/legacy" \
pi --no-extensions -e "$PWD/index.ts"

进入 Pi 后，先 /rag config、/rag status，再用示例文档执行 /rag index <绝对路径> 与 /rag search <问题>。当结果和来源符合预期，再执行 /rag on。密钥只通过 VOYAGE_API_KEY 环境变量传入，不写入两个 JSON 文件。Provider 定义见 provider.json，密钥解析见 provider-config.ts。

如果要使用兼容 Voyage 协议的代理，可在当前 store 的 provider.json 中定义新 key、type: "voyage"、baseUrl、auth.env 与模型维度，然后在 config.json 中选择该 key。可先阅读已有的 Provider 源码阅读课，再修改自己的项目配置。

7. 遇到问题时怎么判断

看到什么先查什么下一步
config.json is invalid/rag config手工修正 JSON；若要恢复默认，/rag config reset 会先保留 .broken-* 备份。
Rebuild needed: yes/rag status 的 wanted/active 模型与 reason确认 tracked paths 后运行 /rag rebuild --force；完成后重新查询。
degraded 或 bm25-fallback密钥、网络、Embedding 服务与错误文本结果可能只来自关键词检索，不要当成完整的混合检索成功。
刷新拒绝或资料缺失/rag status 的 tracked paths先恢复不可访问的路径；程序会拒绝因扫描失败而误删旧索引。
搜索不到应有内容Storage、扩展名、exclude、文件是否真的索引先 /rag find，再 /rag refresh；改了排除规则则 /rag rebuild。

全量重建会先在 staging 生成新索引，成功且向量覆盖完整后才切换 active.json；失败不会发布 staging。这个保护不等于“所有数据都备份好了”，仍要留意实际 Storage 路径。实现见 indexing.ts 的 rebuildWithSwitch 和 index-manager.ts 的 finalizeStaging。

8. 沿一次真实提问读源码

  1. index.ts 的 before_agent_start 先读取配置、检查开关与索引兼容性。
  2. retrieval.ts 的 retrieve 调用 search.ts 的 hybridSearchDetailed，再按配置尝试 Rerank。
  3. providers/embedding/factory.ts 为活动索引选择对应 Embedding Provider；查询不能随意改用另一套维度。
  4. context.ts 的 buildContext 将检索片段压入上下文预算，并保留可读的来源位置。
  5. 在 Pi 中手动执行 /rag search 或让 Agent 调用 rag_query，走的是同一检索入口，但输出形式不同。

继续深入：云端 Provider 代码阅读课 从 Registry、Factory、HTTP 请求讲到 Fingerprint。

9. 三个自检问题

  1. 执行 /rag off 后，/rag search 还能不能用？原因是什么？
  2. 把 embedding 从本地 384 维改为 Voyage 1024 维后，为什么不能沿用旧向量索引？
  3. /rag status 显示正确的 Storage，但结果标了 bm25-fallback。此时你已经验证了什么，还没验证什么？

你可以先按本页完成一次小试用，再回答这三问；页面完成不代表已经掌握。
