SOURCE WALKTHROUGH / 01

把“云端 Provider”从一段硬编码，读成一条可追踪的数据流

这篇教程针对当前仓库的真实实现：从 provider.json 的查找开始，沿着配置解析、Provider 工厂、Voyage HTTP 请求，一直走到索引兼容性和 Pi Extension 的自动注入。重点不是记住文件名，而是理解每一步为什么存在。

代码：pi-local-rag主题：云端 Embedding + Reranker前置：会读 TypeScript 基础
先记住一句话：config.json 负责“选谁”，provider.json 负责“这个 Provider 是什么、能选哪些模型”，TypeScript 适配器负责“怎样把请求发出去”。

01 · 先看全局：三个文件各自负责什么

第一次读这类改造，最容易把“配置”“Provider 实例”“HTTP 协议”混在一起。先把职责拆开，后面的代码会非常清楚。

文件它回答的问题它不负责什么
config.json当前这次 RAG 要用哪个 Provider、哪个 Model？不保存 API Key；不定义模型完整目录。
provider.json有哪些 Provider？它们的地址、鉴权环境变量和模型元数据是什么？不实现 HTTP 请求；不保存密钥值。
providers/**/*.ts如何构造请求、发送请求、解析响应、处理取消和重试？不负责决定用户选择了哪个模型。

当前默认的 Provider Registry 在 pi-local-rag/provider.json。其中有三个不同层次的 ID：

config.json embedding.provider = "voyage" │ ▼ provider.json providers.voyage.type = "voyage" providers.voyage.baseUrl = "https://api.voyageai.com/v1" providers.voyage.auth.env = "VOYAGE_API_KEY" │ ▼ TypeScript adapter VoyageEmbeddingProvider / VoyageReranker

因此，Provider Registry Key 不一定等于适配器类型。比如未来可以出现：

{
  "providers": {
    "company-proxy": {
      "type": "voyage",
      "baseUrl": "https://proxy.example.com/v1",
      "auth": { "type": "bearer", "env": "COMPANY_VOYAGE_KEY" },
      "models": {
        "embedding": { "voyage-4-lite": { "dimensions": 1024 } },
        "rerank": { "rerank-2.5-lite": {} }
      }
    }
  }
}

company-proxy 是用户可读的配置名，voyage 是实际协议适配器名。这正是 Provider 抽象存在的意义：地址可以换，名称可以换，但协议实现不必重复复制。

02 · 配置文件从哪里来：精确的查找顺序

入口是 store.ts 的 getRagDir()。它先决定“当前 RAG 数据属于哪个目录”，然后 provider-config.ts 才在这个目录下找 provider.json。

pi-local-rag/store.ts · getRagDir() / providerFile()
export function providerFile(ragDir: string): string {
  return join(ragDir, "provider.json");
}

当前 RAG 目录的优先级是：

  1. --rag-dir 显式参数；
  2. PI_RAG_DIR 环境变量；
  3. 从当前工作目录向上寻找已经存在的 .pi/rag/；
  4. 否则使用 ~/.pi/rag/ 全局目录。

接着，providerFilePath() 使用下面的策略：

pi-local-rag/provider-config.ts · providerFilePath() · 约第 66 行
export function providerFilePath(): string {
  const local = providerFile(getRagDir());
  if (existsSync(local)) return local;

  return fileURLToPath(
    new URL("./provider.json", import.meta.url),
  );
}

它的真实含义是：

<当前 RAG 目录>/provider.json │ 存在 → 使用项目/全局覆盖文件 │ 不存在 ▼ provider-config.ts 同目录/provider.json │ 使用随 Extension 发布的默认 Registry
注意：这里不是递归搜索当前代码目录的所有子目录。不会扫描 ./src/provider.json、./config/provider.json 等路径；只会检查两个固定位置。

而且项目文件一旦存在，就完全替代内置文件，不会和内置 Registry 深度合并。原因是合并后用户很难判断最终生效的模型目录；明确的全量覆盖更容易排查问题。

03 · 加载 Registry：JSON 如何变成类型安全的对象

loadProviderFile() 做三件事：确定文件路径、解析 JSON、验证最外层结构。它不是把所有字段都强行转换，而是先阻止明显错误进入 Factory。

pi-local-rag/provider-config.ts · loadProviderFile() · 约第 84 行
const providers: Record = {};

for (const [id, value] of Object.entries(raw.providers)) {
  if (!isRecord(value) ||
      typeof value.type !== "string" ||
      !isRecord(value.models)) {
    throw new ProviderConfigError(
      `Provider "${id}" must define type and models in ${file}.`,
    );
  }

  if (!["transformers", "voyage", "noop"].includes(value.type)) {
    throw new ProviderConfigError(
      `Provider "${id}" has unsupported type "${value.type}".`,
    );
  }

  providers[id] = value as unknown as ProviderDefinition;
}

几个细节要特别理解：

  • isRecord() 排除数组和 null，避免把错误结构当成 Provider。
  • version: 1 是 Registry 格式版本，不是 API Key 版本，也不是模型版本。
  • type 目前只允许已有适配器：transformers、voyage、noop。
  • 解析失败会抛出 ProviderConfigError，不会偷偷退回 Voyage 默认值。

getModelSpec：不读取密钥的元数据查询

getModelSpec() 只回答“这个 Provider 有没有这个角色、这个模型，它的类型、地址和维度是什么”。它不要求环境变量已经存在。

pi-local-rag/provider-config.ts · getModelSpec() · 约第 134 行
const provider = file.providers[providerId];
if (!provider) {
  throw new ProviderConfigError(
    `Unsupported ${role} provider "${providerId}".`,
  );
}

const definition = requiredModel(provider, providerId, role, model);
return {
  providerId,
  type: provider.type,
  baseUrl: provider.baseUrl,
  model,
  dimensions: definition.dimensions,
};

它适合做配置验证和生成索引 Fingerprint，因为这两个场景需要知道模型元数据，但不应该在“只读状态”阶段就因为缺少 API Key 而失败。

resolveModel：真正创建 Provider 前解析凭据

resolveModel() 在 getModelSpec() 的基础上读取 auth.env 指向的环境变量：

pi-local-rag/provider-config.ts · resolveModel() · 约第 157 行
if (provider.auth) {
  const value = process.env[provider.auth.env];
  if (!value) {
    throw new ProviderConfigError(
      `${provider.auth.env} is required by provider "${providerId}".`,
    );
  }
  spec.apiKey = value;
}

所以密钥永远只存在于进程内存里：

provider.json auth.env = "VOYAGE_API_KEY" ← 只存变量名 │ ▼ process.env.VOYAGE_API_KEY ← 运行时读取真实值 │ ▼ spec.apiKey ← 只传给适配器，不写回 JSON

这就是为什么 Provider 可以换别名、换代理、换密钥变量，而不需要改 VoyageEmbeddingProvider 的鉴权代码。

04 · Factory：把“配置对象”变成“可调用对象”

Factory 是整个改造的中心。它不直接发 HTTP，而是把 Registry 中的 type 映射到已有实现。

pi-local-rag/providers/embedding/factory.ts · createEmbeddingProvider() · 约第 86 行
export function createEmbeddingProvider(
  config: RagConfig = loadConfig(),
): EmbeddingProvider {
  assertValidConfig(config);

  const spec = resolveModel(
    config.embedding.provider,
    "embedding",
    config.embedding.model,
  );

  const dimensions = spec.dimensions;
  if (dimensions === undefined) {
    throw new Error("Embedding model has no dimensions in provider.json");
  }

  return cached(cacheKey({ /* ... */ }), () =>
    buildProvider({
      id: spec.providerId,
      type: spec.type,
      baseUrl: spec.baseUrl,
      model: spec.model,
      dimensions,
      apiKey: spec.apiKey,
      timeoutMs: config.http.timeoutMs,
      maxRetries: config.http.maxRetries,
    }),
  );
}

按执行顺序拆开：

  1. assertValidConfig(config)：确认 RAG 的普通配置和 Provider Registry 没有明显错误。
  2. resolveModel()：把 Provider ID 和 Model 名称变成具体规格。
  3. 取 dimensions：SQLite 向量表必须知道维度，不能让 Provider 自己临时猜。
  4. cacheKey()：用完整合同生成缓存键。
  5. buildProvider()：根据 spec.type 创建具体类。

为什么缓存键要包含 Base URL 和 HTTP 参数

缓存键不是简单的 provider + model：

[
  opts.id,
  opts.type,
  opts.baseUrl ?? "",
  opts.model,
  opts.dimensions,
  opts.apiKey ?? "",
  opts.http.timeoutMs,
  opts.http.maxRetries,
].join("|")

原因是 Provider 实例内部持有 endpoint、API Key、超时和重试策略。如果只按模型名缓存，修改代理地址后可能继续使用旧实例。缓存的是完整可复用合同，不是只缓存一个名字。

type 如何映射到实现

pi-local-rag/providers/embedding/factory.ts · buildProvider() · 约第 41 行
if (opts.type === "transformers") {
  return new LocalEmbeddingProvider({
    model: opts.model,
    dimensions: opts.dimensions,
  });
}

if (opts.type === "voyage") {
  return new VoyageEmbeddingProvider({
    id: opts.id,
    baseUrl: opts.baseUrl,
    model: opts.model,
    dimensions: opts.dimensions,
    apiKey: opts.apiKey,
  });
}

这就是“配置驱动”的边界：JSON 可以选择和参数化已有适配器，但不能凭空创造一个未知 HTTP 协议。未来若要接 OpenAI-compatible 或 Cohere，需要新增对应的 type 和请求/响应解析代码。

05 · Voyage 适配器：配置如何进入真实 HTTP 请求

Factory 只把配置传给 VoyageEmbeddingProvider。真正拼接 endpoint、构造 body、调用 HTTP 工具的是 Voyage 类。

pi-local-rag/providers/embedding/voyage.ts · constructor / requestBatch()
this.endpoint =
  `${(opts.baseUrl ?? DEFAULT_BASE_URL).replace(/\/+$/, "")}/embeddings`;

例如：

provider.json 的 baseUrl最终 Embedding endpoint
https://api.voyageai.com/v1https://api.voyageai.com/v1/embeddings
https://proxy.example.com/v1/https://proxy.example.com/v1/embeddings

构造请求体时，Provider 配置中的模型和维度被放进 Voyage API 所需字段：

const body = {
  input: texts,
  model: this.model,
  input_type: inputType,
  truncation: false,
  output_dtype: "float",
  output_dimension: this.dimensions,
};

const json = await postJson(this.endpoint, body, {
  apiKey: this.apiKey,
  timeoutMs: this.timeoutMs,
  maxRetries: this.maxRetries,
  signal,
});

这里要注意三个层次：

  • model 来自 config.json 选择的模型，并经过 provider.json 验证。
  • output_dimension 来自 provider.json 的模型元数据。
  • apiKey 来自 auth.env 指定的环境变量。

因此，provider.json 不是一个“只改变名字”的配置；它会影响最终发送给服务端的模型、维度和地址。

Reranker 为什么是另一条路径

Reranker 不负责生成向量，只负责给候选文档重新排序。它复用同一套 Registry 解析，但 Factory 选择 VoyageReranker：

pi-local-rag/providers/reranker/factory.ts · createReranker() · 约第 25 行
const spec = resolveModel(
  config.reranker.provider,
  "rerank",
  config.reranker.model,
);

if (spec.type === "noop") return new NoneReranker();
if (spec.type === "voyage") {
  return new VoyageReranker({
    id: spec.providerId,
    baseUrl: spec.baseUrl,
    model: spec.model,
    apiKey: spec.apiKey,
  });
}

Rerank 请求体是：

{
  query,
  documents: candidates.map(c => c.text),
  model: this.model,
  top_k: opts?.topK ?? candidates.length,
  truncation: false,
}

Embedding 和 Rerank 共用 Provider 选择机制，但使用不同的 endpoint、请求字段和响应解析。这是正确的抽象边界：配置统一，不代表业务协议也必须相同。

06 · Fingerprint：为什么换了 endpoint 也必须重建索引

如果只把 Provider、Model 和维度写进索引指纹，会漏掉一个危险情况：Provider 名称没变，但 Base URL 换了。代理可能返回不同向量空间，旧索引就不能安全地和新查询向量混用。

pi-local-rag/fingerprint.ts · providerContractHash() · 约第 34 行
return createHash("sha256")
  .update(JSON.stringify({
    provider: embedding.provider,
    type: spec.type,
    baseUrl: spec.baseUrl ?? "",
    model: embedding.model,
    dimensions: spec.dimensions ?? embedding.dimensions,
  }))
  .digest("hex")
  .slice(0, 16);

这里刻意没有把 API Key 放入 hash。密钥变化不应该让索引失效；Endpoint、协议类型、模型和维度变化则可能影响向量语义，应该触发重建。

完整 Embedding Fingerprint 大致是：

{
  provider: "voyage",
  model: "voyage-4-lite",
  dimensions: 1024,
  providerContract: "非密钥配置摘要",
  contract: "l2-unit-v1"
}

旧索引没有 providerContract 时，代码允许按照旧的 Provider/Model/Dimensions 逻辑继续兼容；新旧两边都有摘要后，摘要不一致就会要求重建。

兼容性检查在哪里发生

pi-local-rag/index-manager.ts · checkIndexCompatibility() · 约第 85 行

它拿当前配置生成 desiredEmb，再和数据库 metadata 中保存的 storedEmb 比较。以下情况会返回 needsRebuild：

  • 数据库没有 Fingerprint；
  • 向量表维度和配置不一致；
  • Provider、Model、维度或 Provider Contract 不一致；
  • 解析器或 Chunker 的 Processing Fingerprint 不一致。

重建时不是直接覆盖旧库，而是先写 staging 数据库，成功后更新 active.json。因此 Provider 配置错误或云端请求失败时，旧索引仍然可以保留。

07 · 检索链路：Provider 如何参与一次查询

一次查询大致经过下面的路径：

Pi 用户问题 │ ▼ before_agent_start / rag_query │ ▼ loadConfig() → loadProviderFile() → resolveModel() │ ├── Embedding: createEmbeddingProvider() │ └── embedQuery() → Voyage /embeddings │ ├── BM25: SQLite FTS5 │ └── Reranker: createReranker() └── Voyage /rerank（如果启用）

检索实现位于 retrieval.ts。它不会直接判断 Provider 名字是不是 voyage，而是问 Factory“这个配置对应什么类型”：

pi-local-rag/retrieval.ts · retrieveWithCandidates() · 约第 42 行
if (configuredRerankerIsEnabled(config)) {
  try {
    reranker = createReranker(config);
    expand = reranker.id !== "none";
  } catch (err) {
    rerankDegraded =
      `reranker unavailable: ${err instanceof Error ? err.message : String(err)}`;
    reranker = new NoneReranker();
  }
}

因此一个 Provider 别名也不会影响“是否启用 Rerank”的判断，判断依据是 Registry 中的 type。当 Rerank 不可用时，检索不会直接崩溃，而是保留 BM25/向量结果并附带 degraded 信息。

Embedding 失败时为什么可以 BM25 降级

Embedding Provider 抛出的错误会在 search.ts 的向量查询阶段被识别。对于网络错误、超时、429、5xx 等临时问题，代码保留 FTS 结果，并把原因写入 embedDegraded。

try {
  const provider = embeddingProviderForIndex(database, config);
  const queryVec = await provider.embedQuery(query, { signal });
  vecResults = repo.searchVectors(database, queryVec, vecLimit);
} catch (err) {
  if (isTransientEmbedError(err)) {
    embedDegraded =
      `query embedding failed, BM25 only: ${err.message}`;
  } else {
    throw err;
  }
}

这里体现了 Provider 抽象和业务降级的分离：适配器只报告“调用失败”，检索层决定“失败后是否继续用 BM25”。

08 · Extension 入口：Provider 何时真正被触发

index.ts 是 Pi Extension 的注册入口。它本身不实现 Voyage 协议，只负责把 Provider 系统接到 Pi 的生命周期和工具上。

pi-local-rag/index.ts · before_agent_start() · 约第 125 行

每轮 Agent 开始前，它会：

  1. 读取 config.json；
  2. 检查当前索引是否兼容；
  3. 必要时触发自动刷新；
  4. 调用 retrieve()；
  5. 把结果包装成隐藏的 RAG 上下文消息返回给 Pi。
const compat = checkIndexCompatibility(database, config);
if (!compat.ok) {
  // 不使用不兼容的旧向量
  return;
}

results = await retrieve(event.prompt, {
  limit: config.ragTopK,
  alpha: config.ragAlpha,
  db: database,
  config,
  signal,
});

所以用户看到的命令和工具只是入口，真正的云端调用发生在下面的业务方法中：

Pi 入口调用链Provider 什么时候出现
/rag index / rag_indexindexFiles() → createEmbeddingProvider()为文档生成 Embedding。
/rag search / rag_queryretrieveWithCandidates() → embeddingProviderForIndex()为查询生成向量；可选 Rerank。
before_agent_start自动刷新 + retrieve()每轮对话可能触发查询或刷新。
/rag status / rag_status读取配置和索引状态展示 Provider/Model/维度，不一定发云端请求。

09 · 完整走一遍：默认 Voyage 的实际过程

  1. 读取 config.json

    假设配置为：

    {
  "embedding": {
    "provider": "voyage",
    "model": "voyage-4-lite",
    "dimensions": 1024
  },
  "reranker": {
    "provider": "voyage",
    "model": "rerank-2.5-lite"
  }
}

    loadConfigDetailed() 读取这个选择，并调用 validateConfig()。

  2. 找到 Registry

    providerFilePath() 找到 <ragDir>/provider.json；如果不存在，找到 provider-config.ts 同目录的内置 Registry。

  3. 验证模型和密钥

    getModelSpec("voyage", "embedding", "voyage-4-lite") 得到 type: "voyage"、baseUrl 和 dimensions: 1024；resolveModel() 再读取 VOYAGE_API_KEY。

  4. 创建 Embedding 对象

    createEmbeddingProvider() 计算缓存键，buildProvider() 创建 VoyageEmbeddingProvider。

  5. 生成文档向量

    indexFiles() 读取文件、切块，然后调用 embedDocuments()。Voyage 类按批次请求 /embeddings，按返回的 index 放回原输入位置。

  6. 检查并写入索引

    数据库保存 chunks 和 vectors，同时写入 Embedding Fingerprint。维度不匹配、响应缺项或请求失败时，不会把不完整结果发布为活动索引。

  7. 执行查询

    embeddingProviderForIndex() 从活动索引 Fingerprint 读取历史 Provider/Model，再从当前 Registry 重新解析它，生成 query vector，然后和 SQLite 向量结果、FTS 结果合并。

  8. 可选 Rerank

    如果 Reranker 的类型不是 noop，Factory 创建 Voyage Reranker，对候选文本调用 /rerank；失败则返回原始候选，并附带降级原因。

10 · 你可以配置什么，不能配置什么

现在可以做到

  • 默认 Voyage Embedding；
  • 默认 Voyage Reranker；
  • 为 Voyage 协议配置别名；
  • 替换兼容 Voyage 的 Base URL；
  • 替换 API Key 环境变量名；
  • 在 Registry 中增加多个 Voyage-compatible 模型；
  • 让本地、noop 和云端 Provider 走统一配置校验。

现在还不能只靠 JSON 做到

  • 自动发现远端模型列表；
  • 自动把任意 OpenAI/Cohere/Jina API 转成当前请求格式；
  • 在 JSON 中描述任意复杂认证流程；
  • 为每种模型自由编写完全不同的 body 和响应解析逻辑。
最重要的边界：provider.json 统一的是“Provider 注册和配置”，不是“所有云端协议的实现”。新的 wire protocol 仍然需要新的 TypeScript adapter。

11 · 自检：读懂这套代码的五个问题

  1. 如果 .pi/rag/provider.json 不存在，代码会去哪里找？
  2. config.json 中的 provider: "my-voyage" 是否必须等于 type: "voyage"？
  3. 为什么 getModelSpec() 不读取 API Key，而 resolveModel() 要读取？
  4. 如果只修改了 baseUrl，为什么索引需要重建？
  5. Voyage Embedding 失败时，为什么检索可以退回 BM25，而维度不匹配时不能继续？

如果能回答这五个问题，你应该能够从任意一个入口文件开始，反向追踪到 Provider Registry、Factory、HTTP 适配器和索引发布。

  5. 最后再尝试把一个新的非 Voyage 协议接入，明确列出它需要新增的 adapter 接口。
